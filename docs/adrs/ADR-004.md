# Título: ADR-004 - Implementación de Patrón Circuit Breaker para Pasarela de Pagos

**Estado:** Propuesto
**Fecha:** 2026-06-17
**Decisores:** Nabil Chattich
**Relacionado:** Issue #24

## Contexto
- **Qué problema se está resolviendo:** Dificultades al tratar con APIs externas en el control de errores[cite: 2]. Específicamente, cuando la pasarela de cobro externa se cae o responde lento, bloquea los hilos de nuestra aplicación, provocando que todo el sistema de ReviroLabs deje de responder.
- **Qué restricciones aplican:** No podemos controlar la disponibilidad del proveedor externo, pero debemos proteger nuestra infraestructura de sus caídas.
- **Qué datos de proyecto sustentan la decisión:** Las pruebas de estrés demostraron que si el servicio de pago tarda más de 10 segundos, los usuarios recargan la página, triplicando la carga del servidor.

## Decisión
**Qué se decide exactamente:**
- Implementar el patrón Circuit Breaker (Cortocircuito)[cite: 3] utilizando una librería como `opossum` en Node.js para las llamadas al servicio de pagos.
- **Alcance:** Aplica únicamente a las integraciones con APIs de terceros (como MercadoPago o Stripe). No aplica a consultas internas a nuestra propia base de datos.

## Alternativas consideradas
- **Opción A: Reintentos simples (Retries).** Pros: Fácil de programar. Contras: Empeora el problema si el servicio externo está caído, ya que lo sobrecarga aún más y sigue bloqueando nuestros recursos.
- **Opción B: Colas de Mensajes.** Pros: Desacopla el pago[cite: 3]. Contras: Cambia el flujo del usuario (no sabe si su pago se aprobó al instante), requiriendo rediseñar el frontend.
- **Opción C: Circuit Breaker (Seleccionada).** Pros: Previene fallos en cascada al cortar la conexión automáticamente (Estado Open) y permite probar paulatinamente si el servicio volvió (Estado Half-Open)[cite: 3]. Falla rápido y le avisa al usuario al instante.

## Consecuencias
- **Beneficios esperados:** Aislamiento de fallos. El resto del catálogo de eventos seguirá funcionando perfectamente aunque los pagos estén temporalmente caídos.
- **Costos o riesgos que se aceptan:** Complejidad adicional en la configuración del cliente HTTP.
- **Impacto en operación y equipo:** Hay que definir correctamente los umbrales (ej. cuántos fallos seguidos abren el circuito y cuánto tiempo esperar antes de intentar de nuevo).

## Plan de implementación
- **Pasos mínimos para ejecutarla:** Instalar la librería correspondiente, envolver la función que hace el llamado HTTP externo dentro del Circuit Breaker, y configurar un mensaje de error amigable ("Servicio de pagos no disponible, intente en unos minutos") como respuesta de contingencia.

## Dependencias
- Librería de Circuit Breaker compatible con Express.js.

## Métrica de éxito
- En caso de caída del proveedor de pagos, el tiempo de respuesta del endpoint hacia el cliente no debe superar 1 segundo (fallando rápido).

## Triggers de revisión
- **Qué condiciones obligan a reabrir esta ADR:** Si los falsos positivos (circuitos abriéndose por un único micro-corte) afectan la tasa de conversión de ventas.
