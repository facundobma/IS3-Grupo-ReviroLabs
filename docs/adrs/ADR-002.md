# Título: ADR-002 - Implementación de Caché para Catálogo de Eventos

**Estado:** Propuesto
**Fecha:** 2026-06-17
**Decisores:** Facundo Balmaceda
**Relacionado:** Issue #20

## Contexto
- **Qué problema se está resolviendo:** Latencia alta en la consulta del endpoint del catálogo de eventos públicos debido al volumen de tráfico de lectura recurrente.
- **Qué restricciones aplican:** Se debe mejorar la velocidad de respuesta sin sobrecargar el motor de base de datos principal (MySQL).
- **Qué datos de proyecto sustentan la decisión:** Las lecturas del catálogo de eventos superan a las escrituras en un ratio de 100:1. La consulta a la DB es costosa por la cantidad de filtros aplicables.

## Decisión
**Qué se decide exactamente:**
- Integrar Redis como sistema de caché en memoria.
- **Alcance:** Cubre únicamente las peticiones de lectura del catálogo público de eventos (estrategia cache-aside). No aplica a los flujos de checkout o reservas.

## Alternativas consideradas
- **Opción A: Replicación de DB.** Pros: Separa lecturas de escrituras. Contras: Mayor costo de infraestructura y complejidad operativa para este problema puntual.
- **Opción B: Memcached.** Pros: Muy rápido para cacheo simple. Contras: Menos estructuras de datos soportadas comparado con Redis.
- **Opción C: Redis (Seleccionada).** Pros: Extremadamente rápido, permite TTL (Time To Live) nativo, evita consultas costosas repetidas en la base de datos relacional.

## Consecuencias
- **Beneficios esperados:** Reducción drástica de la latencia en las lecturas, liberando recursos valiosos en el servidor MySQL.
- **Costos o riesgos que se aceptan:** Riesgo de servir datos ligeramente desactualizados ("stale data") hasta que la caché expire (TTL).
- **Impacto en operación y equipo:** Se añade un nuevo componente a la infraestructura (nuevo contenedor Docker a mantener). El backend debe implementar la lógica de invalidación de caché.

## Plan de implementación
- **Pasos mínimos para ejecutarla:** Añadir el servicio `redis` al archivo `docker-compose.yml`. Instalar la librería cliente de Redis en el backend e implementar un middleware de caché en los endpoints de lectura del catálogo.

## Dependencias
- Instancia de Redis y librería de cliente para Node.js.

## Métrica de éxito
- Reducción del tiempo de respuesta del catálogo en un 80% (de ~500ms a < 50ms).

## Triggers de revisión
- **Qué condiciones obligan a reabrir esta ADR:** Si el costo de mantener la instancia de Redis supera el beneficio o si los usuarios reportan problemas severos por ver datos inconsistentes.
